# HypEvolve — Experiment Design

**Date:** 2026-08-25  
**Status:** Approved  
**Type:** Empirical experiment and research framework

## Overview

HypEvolve combines genetic algorithms (GA) with LLM coding agents exposed through CLIs to optimize real software performance. Each population individual is a code variant owned by a persistent agent session; the GA empirically validates hypotheses generated by the LLM.

The framework supports a rigorous study suitable for publication and provides infrastructure for a future autonomous software-improvement agent.

## Positioning

| Work | What it does | HypEvolve distinction |
|---|---|---|
| Genetic Improvement | Evolves code through syntactic mutations | LLM hypotheses guide mutations |
| FunSearch | Combines LLMs and evolution to discover mathematical functions | Improves existing software and records explicit hypotheses |
| AlphaEvolve | Evolves agents for algorithm discovery | Persistent individual sessions accumulate context |
| EoH / ReEvo | Evolves heuristics with LLMs | Targets existing-code optimization rather than heuristics |

## Contributions

1. Every patch carries an explicit textual hypothesis that is empirically validated and fed back into the search.
2. Every individual is a persistent CLI-agent session with its own workspace, so context accumulates across generations.
3. Evaluation uses the same budget for strong baselines, including one-shot LLM attempts and random search.

## Research questions

- **RQ1:** Does a GA+LLM loop with explicit hypotheses improve performance more than direct LLM optimization and random search under the same budget?
- **RQ2:** Is the gain independent of the generating LLM or agent?
- **RQ3:** Does hypothesis tracking accelerate convergence compared with an ablation without the tracker?

## Metrics

- **Primary:** relative speedup in target benchmark execution time.
- **Secondary:** evaluations to reach improvement thresholds, functional-patch rate, token and dollar cost, and best fitness per generation.

## Architecture

```text
Orchestrator (GA loop)
├── Agent Session Manager   — one persistent CLI session per individual
├── Workspace Manager       — isolated project copy per individual
├── Evaluator               — correctness tests and benchmark fitness
├── Fitness + Statistics    — significance gate against the parent
├── Selector                — elitism and tournament selection
└── Hypothesis Tracker      — confirmed, refuted, and inconclusive evidence
```

### Per-generation flow

1. The selector chooses parents.
2. A mutation prompt sends parent state, fitness, profiling hotspots, and tested hypotheses to the parent session and requests a structured hypothesis and patch.
3. The agent edits its own workspace.
4. The evaluator checks correctness and measures performance. A broken patch receives zero fitness.
5. Fitness and statistics compare the child with its parent using a significance test.
6. The hypothesis tracker records the outcome.
7. Removed individuals close their sessions; new individuals inherit the parent's summary.

## Technical decisions

- Python 3.12 or newer.
- LLM integration uses persistent agent CLIs only; there are no direct provider SDK calls or `litellm` dependencies.
- Each individual receives an isolated workspace; subprocesses have timeouts and resource limits.
- Every prompt, response, and session transcript is stored as experiment data.
- Exact CLI and model versions are pinned in experiment configurations.
- Formal state contracts use `icontract`; strict Pyright and CrossHair run in the lint gate.

## Experimental protocol

- **Targets:** 4–6 small or medium open-source Python repositories with test suites and identifiable performance hotspots.
- **GA configuration:** population around 8, 10–15 generations, elitism of 1, and tournament selection.
- **Fixed budget:** approximately 100 evaluations per run, identical across conditions.
- **Conditions:** one-shot/few-shot LLM baseline, random syntactic mutation baseline, full GA+LLM treatment, and an RQ3 ablation without hypothesis tracking.
- **Statistical rigor:** 30 independent runs per condition (15 in the pilot), Mann–Whitney U or Kruskal–Wallis with Bonferroni correction, Vargha–Delaney A12 or Cliff's delta, and repeated benchmarks with warm-up and documented outliers.

## Roadmap

1. Set up the repository and select target projects using objective criteria.
2. Implement the minimal framework: GA loop, CLI sessions, evaluator, and tracker.
3. Run the pilot and validate the pipeline and cost.
4. Execute all experimental conditions.
5. Perform statistical analysis.
6. Write the paper.

## Out of scope

- Multi-objective optimization of cost and code quality.
- A continuously autonomous production-improvement loop.
